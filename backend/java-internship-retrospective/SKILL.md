# Java 实习复盘与亮点

从当前会话及可访问的代码改动、测试结果、日志中提取事实。任务已完成或用户明确要求总结时，默认生成一条每日进度、问题复盘日报、Java 简历亮点和离线可打开的 HTML 复盘网页；全部生成并核验后，统一归档到独立目录。除非用户明确要求，不覆盖已有文件。

## 工作流

1. 收集可验证证据：用户描述、会话中的排查过程、代码改动、命令输出、测试与日志。
2. 识别主题。使用最具体、简短的中文或英文主题；无法判断时使用 `问题修复`。
3. 判断任务状态：未完成、仅排查中或证据不足时，只提供阶段性总结，不写入“已完成”进度；完成或用户明确要求写日报时再写入全部文档。
4. 生成每日进度、复盘日报、简历亮点和复盘网页，完成事实核验与质量检查后，统一保存到归档目录。日期采用执行当天的 `YYYY-MM-DD`。
5. 保存后回复归档目录及四个绝对路径和一行摘要。

## 每日进度

- 汇总文件：`C:\Users\Administrator\Desktop\实习\每日小报\研发部进度记录汇总.md`
- 从已确认事实中提炼一条“任务内容（精简）”，目标 30–50 字，严格不超过 50 个可见中文字符/数字/英文词组；不写日期前缀。
- 使用“动作 + 具体对象 + 结果”，例如：`修复充值协议下发与代金券开关校验，完成前后端跳过战斗联调。`
- 同时维护同一文件中的两个表格，不能只写精简版：
  - 上方完整明细表追加或更新 `| YYYY-MM-DD | 项目 | 人员 | 当天任务总结 | 完成情况/结果 |`；项目和人员缺少证据时写“待补充”，任务总结与结果仅陈述已验证事实。
  - `## 可直接填写到表格的精简版` 追加或更新对应的 `| MM-DD | 摘要 |`。
- 先按日期和事项检查两个表是否已有记录；当天已有相同事项时同步更新两处，避免重复或出现明细表与精简表不一致。
- 写入后重新读取两个新增/更新行，确认日期对应、内容一致、完整表不含未验证结论且精简摘要不超长。不写“参与”“负责”“进行了”等空泛词，也不将待验证事项写成已解决。

## 复盘网页（默认生成）

### 图表生成

当复盘涉及三个或以上存在依赖关系的步骤，或用户要求展示流程、时序、请求链路、数据流或状态变化时，配合 `archify` skill 生成图表：

- 流程、排查步骤、分支和验收路径使用 `workflow`；
- 接口调用、事件发布、Service/DAO/数据库先后关系使用 `sequence`；
- 组件、服务、数据库边界关系按实际需要使用 `architecture` 或 `dataflow`。

图表必须基于已核实的代码、协议、日志和数据库证据；证据不足的节点标记“待补充”，不得猜测客户端入口或协议号。为每张图保留 Archify JSON 源文件，并使用 Archify 的 `validate` 和 `deliver` 命令校验、渲染为离线 HTML。最终复盘网页可以内嵌 SVG，也可以同时归档独立的流程图 HTML、时序图 HTML；不要只交付无法直接查看的 JSON。

推荐输出目录结构：

```text
复盘归档/YYYY-MM-DD-主题/
├── README.md
├── 最终执行计划.md
├── Java后端实习亮点.md
├── 复盘网页.html
├── <主题>.workflow.json
├── <主题>.workflow.html
├── <主题>.sequence.json
└── <主题>.sequence.html
```

Archify 生成失败时，保留 JSON 源文件并记录具体校验错误；不得把未通过校验的图表描述为已验证。若只是本机路径或权限问题，优先输出到可写的工作区临时目录，再在获得权限后复制到最终归档目录。

- 归档后的文件名为 `复盘网页.html`。
- 页面以事实为依据，至少包含：需求与边界、问题现象、定位过程与证据、根因、修复方案、验证效果、完整请求链路、风险与回滚、可写入简历的亮点、后续行动清单。
- 生成网页前必须检索项目中的协议源、客户端调用点和服务端入口；请求链路不得仅凭业务描述推测。
- 请求链路优先使用可点击步骤：点击节点后立即展示该步骤说明；除非用户特别要求，不使用等待式自动播放。
- 每条核心链路至少展示并在点击详情中说明：客户端发起类/方法与文件、Request/Response 或 Push 的 protobuf 消息名和协议 ID、服务端 Handler 方法与文件、后续 Service/Actor/Observer 调用、查询或写入的实体/表、返回响应或异步推送的消息。
- 当核心链路包含 3 个或以上有依赖关系的节点时，在复盘网页中内嵌三类 SVG（不依赖外部资源）：完整请求链路图、业务流程图、时序图。图中节点和箭头必须与已核实的代码调用链一致；每个节点提供可点击详情或紧邻说明，标注客户端入口、protobuf 消息/协议号、Handler、Service/Actor/Observer、实体/表、奖励/流水和响应。若某个节点证据不足，使用“待补充”标记，不用猜测补齐。
- SVG 优先使用内联 `<svg>`、`<marker>`、`<text>` 和简单形状，保证离线打开；流程图表达成功、校验失败和重复/幂等分支，时序图表达请求、校验、持久化、发奖和响应的先后关系。图表应服务于理解链路，不替代文字证据，也不使用自动播放或网络图表库。
- 增加“数据库影响”章节：先从 Entity、Repository/DAO、SQL、迁移脚本或实际库结构核验，再列出本需求读取和写入的数据库表。
- 对每张受影响表展示：表用途、关键字段名与类型/默认值、主键或关联键、读取/写入的业务时机、是否新增字段/迁移、旧数据兼容方式、失败或回滚时的数据影响。
- 明确区分“本需求直接写入”“仅查询统计”“现有链路间接更新”“不受影响”的表；不可把配置文件或内存状态误写为数据库变更。
- 若只拿到代码而没有建表 SQL/线上表结构，字段类型、索引、默认值等必须标记“待补充”，并写明需核对的迁移脚本或 `SHOW CREATE TABLE` 证据。
- 对“客户端本地判断、不发独立请求”的场景明确标识本地入口、使用的协议数据来源和后续真正发生服务端通信的结算节点；不要虚构网络请求。
- 若工程缺少客户端代码、协议 ID 或某一段调用证据，页面标记“待补充”，列出需要核对的文件或日志；不得补写未证实的类名、表名或协议号。
- 将“已验证”“待联调/待补充”“发布事故或风险”明确区分，禁止把未完成事项表述为已上线成功。
- 简历亮点使用“动作 + 技术/场景 + 结果/价值”，不虚构用户量、性能数据、影响范围或上线结果。
- 页面为离线单文件 HTML，不依赖接口或网络资源；保存后检查文件存在，并回复绝对路径和一句摘要。

## 日报内容

使用以下标题：

```md
# YYYY-MM-DD 主题日报

## 问题与影响
## 排查过程
## 根因
## 修复内容
## 验证结果
## 影响范围
## 后续改进
```

只陈述已知事实。无法确认的影响或数据写为“待补充”，并说明需要什么证据。

## Java 后端实习亮点内容

使用以下标题：

```md
# YYYY-MM-DD 主题：Java 后端实习亮点

## 可用于简历的亮点
## 可用于日报/周报的简版总结
## 待补充的量化证据
```

- 输出 3–5 条简历 bullet，每条遵循“动作 + 技术或场景 + 结果或价值”。
- 只突出本次证据中实际出现的技术，如 Java、Spring Boot、MySQL、Redis、消息队列、排障、稳定性或性能。
- 不得编造用户数、耗时、QPS、性能提升比例或线上影响；缺失时使用“待补充数据”。
- 用清晰、具体、面向 Java 后端招聘的措辞，避免“参与”“负责”等空泛表述。
